```cpp

#include <cstring>

#include <unistd.h>

#include <sys/socket.h>

#include <netinet/in.h>

#include <arpa/inet.h>

  
  
  

int main(){

    std::cout << "Server starting..." << std::endl;

    int listen_fd=socket(AF_INET,SOCK_STREAM,0);

    if(listen_fd<0){

        std::cerr<<"Failed to create socket"<<std::endl;

        return 1;

    }

    std::cout << "Socket created successfully, fd = " << listen_fd << std::endl;

    close(listen_fd);

    return 0;

}
```
### 问题描述：**为什么`fd=3`**
```bash
ubuntu_user@codeubuntu:~/shared_files/code/CPP$ ./tcp_server 
Server starting...
Socket created successfully, fd = 3
```
### 原因：
因为文件描述符 0、1、2 已经被系统预先占用：
- **0**：标准输入（stdin）
- **1**：标准输出（stdout）
- **2**：标准错误（stderr）
当程序调用 `socket()` 创建第一个套接字时，系统会分配当前可用的最小未使用文件描述符，即 **3**。
## 问题：二
```cpp
struct sockaddr_in server_addr;
memset(&server_addr, 0, sizeof(server_addr));
```
### 问题描述**为什么要用 `memset`**：
### 原因：
我们创建一个局部变量 `server_addr`，它的初始值是随机的（栈上的垃圾数据）。为了确保结构体中未使用的字段（如 `sin_zero`）是干净的，我们用 `memset` 将整个结构体清零。这是一种常见的防御性编程。
## 问题：三
```cpp
server_addr.sin_family = AF_INET;
server_addr.sin_port = htons(8080);
server_addr.sin_addr.s_addr = htonl(INADDR_ANY);
```
### 问题描述**为什么需要`htons`转换？**：
### 原因：
因为不同的 CPU 对多字节整数的存储顺序不同（小端或大端），而网络协议规定使用大端序。所以发送到网络的数据必须转换为网络字节序。htons可以将 16 位整数从主机字节序转换为网络字节序（大端）。
## 问题：四
```cpp
if (bind(listen_fd, (struct sockaddr*)&server_addr, sizeof(server_addr)) < 0) {
    std::cerr << "bind failed" << std::endl;
    close(listen_fd);
    return 1;
}
```
### 问题描述：**为什么`(struct sockaddr*)&server_addr`强制转换？**
### 原因：
因为 `bind` 可以用于多种地址族（IPv4、IPv6、Unix 域等），所以参数类型是通用的 `struct sockaddr *`。我们实际用的是 `struct sockaddr_in`，但它和 `struct sockaddr` 的内存布局兼容（前两个字段相同），所以可以安全转换。

因为监听 socket 和已连接 socket 是不同的。`监听 socket 保持打开`，继续接受新连接；`已连接 socket 用于与特定客户端通信`。

#  阶段二
## 问题：一
### 问题描述：如何让服务器**同时处理多个客户端**？
### 解决方法：
1. **多进程**：`fork` 一个子进程处理每个客户端，父进程继续等待新连接。
2. **多线程**：`pthread_create` 创建新线程处理每个客户端，主线程继续 `accept`。
3. **I/O 多路复用**：使用 `select`/`poll`/`epoll` 在一个线程内监听多个文件描述符。
## 问题：二
### 问题描述：为什么只用`g++ tcp_server.cpp -o tcp_server` 没有加`-pthread`也能编译成功：
### 原因：
从 glibc 2.34 开始，**pthread 库的函数被直接整合进了 libc 中**，因此编译时不再需要显式链接 `-pthread` 或 `-lpthread`。
## 问题：三
### 问题描述：为什么要用 epoll？
### 原因：
多线程模型虽然简单，但每个客户端需要一个线程，当并发连接数达到几千时，线程创建、切换、内存开销都非常大。  epoll允许一个线程同时监听数百、数千个 socket，只在 socket 就绪（有数据可读、可写等）时才去处理，从而避免了大量线程的浪费。epoll 是 Linux 特有的高效 I/O 多路复用机制，性能远高于传统的 select/poll。
## 问题：四
### 问题描述：为用Windows的cmd使用telnet输入HELLO在服务器上会显示Received from client: HReceived from client: EReceived from client: LLOReceived from client:
### 原因：
Windows 上用 `telnet` 连接服务器，输入 "HELLO" 时，服务器多次收到数据（逐字符），这是 Windows telnet 客户端的默认行为：**每键入一个字符就立即发送**，而不是等待回车后才发送整行。因此，服务器会多次调用 `recv`，每次收到一个字符（或少量字符），导致输出多次 `Received from client: `，而且由于没有换行，输出可能粘连在一起，看起来像是奇怪的拼接。
# 阶段三
## 问题：一
### 问题描述：为什么要学习边缘触发？
### 原因：
之前实现的是 epoll 水平触发（LT）模式： 只要 socket 接收缓冲区有数据，`epoll_wait` 就会持续通知。编程简单，即使你一次没读完，下次还会通知。
边缘触发（ET）模式：只在 socket 状态**发生变化**时通知一次（比如从无数据变为有数据）。 效率更高，减少了内核到用户态的事件拷贝次数。 但要求必须**一次性把数据读完**（循环读直到返回 `EAGAIN`），否则可能漏掉数据。 **必须搭配非阻塞 I/O**，否则如果数据没读完，下次不会再通知，程序就会永远阻塞在 `recv` 上。
## 问题：二
### 问题描述： 为什么要非阻塞？
### 原因：
在边缘触发模式下，当我们收到一个“可读”事件后，我们必须循环调用 `recv` 直到返回 `EAGAIN`（表示缓冲区暂时没有数据了）。  
如果 socket 是阻塞的，那么当缓冲区没有数据时，`recv` 会**阻塞**住，导致程序卡死，无法处理其他连接。  
所以必须用非阻塞模式，让 `recv` 在没数据时立即返回 `-1`，并设置 `errno = EAGAIN`，我们就可以据此停止读取。
## 问题：三
### 问题描述：监听 socket 为什么不用边缘触发？
### 原因： 
新连接事件是离散的，用 LT 更安全；如果使用 ET，每次有连接时只通知一次，若 `accept` 没处理完所有等待连接，可能会漏掉。用 LT 可以确保每次有连接就通知，直到队列为空。
# 阶段四
## 问题：一
### 问题描述：为什么需要调优？
### 原因：
在 Linux 默认配置下，一个进程最多只能打开 1024 个文件描述符（包括 socket），而端口范围、TIME_WAIT 状态等也会限制并发连接数。要通过调整系统参数和内核参数，突破这些限制，让服务器能够处理成千上万的并发连接。
# 阶段五
## 问题：一
### 问题描述：为什么需要多线程 epoll？
### 原因：
我们之前实现的 epoll 边缘触发版本是单线程的，虽然能处理大量连接，但：
只能使用一个 CPU 核心，无法充分利用多核。
如果业务逻辑（如解析协议、处理数据）较重，单线程会成为瓶颈。
多线程 epoll 的常见模式是 Reactor 模式：
主线程：负责监听新连接，然后分发给工作线程。
工作线程池：每个线程拥有独立的 epoll 实例，负责处理一组连接的 I/O 事件。
这样可以将负载分散到多个 CPU 核心上，提升吞吐量。
## 问题：二
### 问题描述：为什么需要 send_buffer？
### 原因：
在非阻塞 I/O 下，send 可能只发送部分数据，我们需要一个地方存放剩余数据，并在可写事件中继续发送。当我们向客户端发送数据时，如果一次 send 没有发完（因为发送缓冲区满），剩下的数据会暂存到std::string send_buffer，等下次可写事件触发时继续发送。
## 问题：三
### 问题描述：为什么工作线程的 epoll 事件循环没有主动唤醒机制？
### 原因：
因为 epoll_ctl 是线程安全的，主线程添加新连接后，工作线程下一次 epoll_wait 会立即返回，无需额外唤醒。如果希望更低延迟，可以使用 eventfd 或 pipe 主动唤醒。
## 问题：四
## 问题描述：为什么使用 data.ptr 而不是 data.fd？
### 原因：
需要存储发送缓冲区等额外信息，所以使用 data.ptr 指向一个结构体，这样可以携带更多状态。
## 问题：五
## 问题描述：为什么在主线程中 new client_info，而在工作线程中 delete？
### 原因：
主线程创建，工作线程消费（处理完成后释放）。由于每个连接只被一个工作线程处理，没有竞争。（生产者-消费者问题）
## 问题：六
### 问题描述：如何选择线程数量？
### 原因：
通常设为 CPU 核数，避免过多线程导致上下文切换开销。可以通过 std::thread::hardware_concurrency() 获取建议值。
# 阶段六
## 问题：一
### 问题描述：为什么只调用一次 recv？
### 原因：
因为 HTTP 请求通常较小，且我们打算在发送响应后立即关闭连接。多次读取没有必要，而且如果客户端发送了大数据（如文件上传），我们也不处理。压测工具 ab 发送的请求很小，一次 recv 足够。
## 问题：二
### 问题描述：为什么发送完后立即关闭连接？
### 原因：
响应中指定了 Connection: close，表示服务器希望关闭连接。主动关闭可以及时释放资源，避免长时间占用。
## 问题：三
### 问题描述：关闭前为什么要先从 epoll 中删除？
### 原因：
如果不删除，后续 epoll_wait 可能返回已关闭 fd 的事件（EPOLLHUP），导致处理逻辑混乱。先删除再关闭是标准做法。
## 问题：四
### 问题描述：为什么在可读事件中发送成功后直接关闭，而在可写事件中也是发送成功后关闭？
### 原因：
无论在哪次发送完成，都意味着响应已全部发出，可以关闭连接。因此统一在发送完成后清理。
# 阶段七：单线程 epoll 服务器的多种实践
## 问题：一
### 问题描述：为什么在实现多线程 epoll 服务器之前，还需要尝试单线程 epoll 的不同实现？
### 原因：
在学习 epoll 的过程中，先掌握单线程版本是必要的：
1. **降低复杂度**：没有多线程的同步问题，更专注于 epoll 的事件驱动模型。
2. **理解不同使用模式**：包括多端口监听、数组索引管理连接、回调函数设计等。
3. **为多线程打下基础**：单线程版本的代码逻辑与多线程 Reactor 模式中的每个工作线程内部非常相似，可以平滑过渡。
4. **验证高并发能力**：单线程 epoll 已经能支撑 C10K（一万并发）级别，足以说明 epoll 的高效性。
## 问题：二
### 问题描述：多端口监听单线程 epoll 服务器解决了什么问题？有哪些特点？
### 原因：
该实现主要展示：
- **多端口服务能力**：单进程同时监听多个端口（如 20 个端口），适用于需要暴露多个服务端口的场景（例如不同服务使用不同端口）。
- **高效连接管理**：使用全局数组 `connlist[1048576]`，直接以文件描述符为索引，避免了动态内存分配，访问速度快。
- **性能埋点**：每处理 1000 个连接打印一次耗时，便于观察连接建立速率。
- **回调分离**：通过函数指针 `accept_cb`、`recv_cb`、`send_cb` 将事件处理逻辑与主循环分离，结构清晰。
这种设计虽然简单，但为后续的 Reactor 模式提供了原型。
## 问题：三
### 问题描述：单线程 epoll HTTP 服务器与多线程版本相比有哪些不足？
### 原因：
1. **无法利用多核 CPU**：所有事件处理都在一个线程中，CPU 利用率有限。
2. **协议处理不够完善**：HTTP 请求解析简单，未处理分块传输、长连接等；响应构造固定，不支持动态内容。
3. **大文件发送存在问题**：未使用 `sendfile` 零拷贝，且未处理 `EAGAIN` 情况，可能导致大文件发送阻塞或截断。
4. **扩展性差**：若业务逻辑（如数据库查询）较重，单线程会阻塞，影响所有连接。
因此，在需要更高性能的场景下，多线程 epoll（Reactor 模式）是更好的选择。
## 问题：四
### 问题描述：单线程 epoll 服务器如何管理大量连接？
### 原因：
通常采用两种方式：
- **全局数组索引**：如上文代码，预先分配 `connlist[1048576]`，直接用文件描述符作为下标访问。这种方式简单高效，但需要提前预估最大连接数。
- **动态分配 + 链表/哈希表**：对于连接数不确定的情况，可以用 `new` 创建连接对象，并通过红黑树或哈希表快速查找。但效率略低于数组索引。
由于 Linux 中文件描述符是递增的，且通常不会超过预设最大值，因此很多高性能服务器（如 Redis）也会采用数组索引方式。
## 问题：五
### 问题描述：单线程 epoll 服务器能否支撑高并发？理论上能支撑多少连接？
### 原因：
单线程 epoll 服务器可以支撑 **C10K（一万并发）** 甚至更高（如 C100K）。主要受限于：
- **系统文件描述符上限**（可通过 `ulimit -n` 调整）。
- **内存**（每个连接需要缓冲区、状态等）。
- **CPU 负载**（如果业务逻辑简单，单线程可以轻松处理数万连接；若业务复杂，则可能成为瓶颈）。
在实际测试中，单线程 epoll echo 服务器在普通 PC 上也能达到数万连接。但若要处理更多连接或复杂业务，多线程版本能更好地利用多核资源。
